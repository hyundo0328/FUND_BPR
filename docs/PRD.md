# PRD — 펀드 기준가 데이터 등록 도구

## Problem Statement

업무운영팀 담당자는 매일 아침 펀드 평가사로부터 이메일로 기준가 txt 파일을 받아,
그 안의 기준가 데이터를 확인한 뒤 사내 펀드 운용시스템에 직접 등록한다.

- 파일이 제때 왔는지 확인하는 것이 번거롭다.
- 파일 내용을 직접 펀드 운용시스템에 등록해줘야 하는 것이 불편하다.

값이 비어있거나 거래기준가가 이상한 항목이 섞여 있으면 평가사에게 다시 확인을 요청해야
하는데, 이런 항목을 눈으로 하나하나 걸러내는 것도 담당자의 몫이었다.

## Solution

기준가 txt 파일을 업로드하면 구분자로 분리해 저장하고, 값 없음·거래기준가 이상 같은
1차 이상 여부를 자동으로 걸러 보여준 뒤, 담당자가 최종 확인 후 펀드 운용시스템에 등록
처리하는 내부 도구. 오늘 파일이 왔는지와 등록 진행 상태를 한 화면에서 바로 확인할 수
있고, 과거에 등록한 기준가 데이터도 조건을 걸어 다시 찾아볼 수 있다. AI 에이전트가
동일한 조회 기능을 MCP 도구로 직접 호출할 수도 있다.

## Features

1. **기준가-파일-업로드** — 펀드 평가사가 보낸 기준가 txt 파일을 업로드하면 구분자로
   분리해 개별 기준가 데이터로 저장한다.
2. **기준가-데이터-확인및등록** — 저장된 기준가 데이터 중 값 없음·거래기준가 이상 등
   1차 규칙으로 걸러진 이상 항목을 보여주고, 담당자가 확인한 정상 항목을 펀드
   운용시스템에 등록 처리한다.
3. **오늘의-등록-현황** — 오늘 기준가 파일이 업로드됐는지, 등록이 얼마나 진행됐는지를
   한 화면에서 확인한다.
4. **등록-이력-조회** — 과거에 업로드·등록된 기준가 데이터를 날짜·펀드 조건으로 검색해
   다시 확인한다.
5. **기준가-조회-mcp-서버** — 기준가 목록 조회, 업로드 상세 조회, 오늘의 등록 현황
   조회를 AI 에이전트가 MCP 도구로 직접 호출할 수 있게 노출한다.

## Scope & Priorities

- **Core** — 기준가-파일-업로드, 기준가-데이터-확인및등록: 담당자가 매일 아침 실제로
  거쳐야 하는 등록 흐름 자체이므로 가장 먼저 갖춰야 한다.
- **Core** — 오늘의-등록-현황: 등록 흐름이 있어야 의미가 생기는 일상 확인 화면으로,
  등록 흐름 다음 우선순위다.
- **Secondary** — 등록-이력-조회: 특정 날짜를 다시 확인해야 하는 드문 상황을 위한
  기능으로, 핵심 등록 흐름이 갖춰진 뒤 붙인다.
- **Secondary** — 기준가-조회-mcp-서버: 사람이 쓰는 화면들이 갖춰진 뒤, 동일한 조회
  기능을 AI 에이전트에도 열어주는 부가 기능이다.

## Out of Scope

- **기준가 파일 지연·미수신 자동 알림** — 파일이 늦거나 오지 않는 경우가 드물어, 알림
  인프라를 구축하는 비용 대비 효용이 낮다고 판단해 제외했다. (`docs/adr/0002`)
- **등록 이력 엑셀·CSV 내보내기** — 조회 화면의 목적(다시 확인하기)을 넘어서는
  기능이라 제외했다. (`docs/adr/0004`)
- **등록 이력 화면 실시간 자동 갱신** — 하루 한 번 등록되는 데이터 특성상 실익이 적어
  제외했다. (`docs/adr/0005`)
- **등록 이력 화면에서의 직접 수정** — 확인및등록 기능과 책임이 겹치고 이력 데이터
  무결성 관리가 복잡해져 제외했다. (`docs/adr/0006`)
- **이상 항목 값의 화면 내 인라인 수정** — 평가사 확인 없이 값이 바뀔 위험이 있어
  제외했다. 정정은 항상 평가사 재확인과 재업로드를 거친다. (`docs/adr/0008`)
- **등록 완료 항목의 취소·롤백** — 이미 펀드 운용시스템에 반영된 값의 정합성을 이
  도구가 책임지기 어려워 제외했다. 잘못 등록된 값은 펀드 운용시스템에서 직접
  정정한다. (`docs/adr/0009`)

## Further Notes

- 오늘의-등록-현황·등록-이력-조회는 별도 테이블 없이 기준가-데이터-확인및등록이 쌓는
  `price_uploads`/`price_records`를 그대로 조회한다. 두 조회 기능은 이 스키마 변경에
  직접 영향을 받는다. (`docs/adr/0007`)
- 1차 이상 판정은 "값 없음"·"거래기준가 비정상(숫자 아님 또는 0 이하)"만 걸러낸다.
  전일 대비 급격한 변동 같은 통계적 이상은 걸러내지 않으므로, 이상 표시가 없다고 해서
  값이 실제로 맞다는 뜻은 아니다 — 최종 판단은 담당자의 몫이다. (`docs/adr/0001`)
- 메일함에서 파일을 내려받아 도구에 올리는 것과, 이상 항목을 평가사에게 재확인
  요청하는 것은 이 도구의 범위 밖이며 담당자가 직접 한다. (`docs/adr/0001`)
- 3-tier 아키텍처(`app/[page]/page.tsx` → `app/api/*/route.ts` → `lib/db.ts` +
  `schema.sql`)를 따르며, 테스트는 API route 핸들러를 직접 호출하는 방식으로
  작성한다(`.claude/rules/testing.md`).
- 이 문서는 임시 문서다. 각 기능이 `/to-spec`으로 spec이 되고 구현·`/spec-retire`를
  거쳐 테스트와 ADR로 이관되면, 모든 기능이 정리된 뒤 이 PRD도 제거한다
  (`.claude/rules/docs.md`).
